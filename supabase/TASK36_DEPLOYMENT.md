Compatibility decisions:

- Legacy `friends` audiences remain in the database and are owner-only. They are never converted to public or automatically to followers. Owners can explicitly edit their audiences. Legacy `friends` tagging preference becomes `nobody`; owners can select the new followers policy.
- Existing restricted profile settings become private accounts. Existing follows remain follows; old friendships/community memberships grant no content access. Pending follow requests are not accepted when switching public.
- After a profile switches to public, a pending request stays pending until that requester explicitly follows again. That explicit follow creates the follow immediately and cancels only that requester's stale pending row. There is no bulk approval on the privacy transition.
- Old auto-created private chats have no consent record. Two-way sender history establishes accepted legacy chat; other legacy chats retain all messages with pending consent. Current follow/contact policy or explicit request acceptance can authorize access. Old IDs cannot bypass this gate.
- Old globally archived chat state is mapped to each current member's archive field; conversations resume a normal server state. New messages stay archived until that viewer unarchives. Mute is independent.
- New group invitees get invitations, not active memberships. Accepted invitees can read initial group history; a removed/left member who is reinvited gets a fresh history boundary. Declined invitations cannot be reopened through an add retry. The group owner transfers to an eligible active member when leaving; when no eligible successor exists despite remaining members, leave fails.
- Empty groups can have no active owner after the last member leaves. Pending invitations from the departed inviter are canceled. Message history is retained.
- Hide/remove decisions change server content state and close the report with an audit entry in one transaction. Remove is a soft content state, preserving existing Cloud rows/media for the normal retention pipeline. Report media preview access is restricted to the reported assets and an authorized reviewer.
- `profiles` raw REST reads deny `bio` and `cover_asset_id` to `PUBLIC`, `anon`, `authenticated`, and `service_role`; authenticated clients keep only the listed safe identity columns under the existing profiles RLS policy. Migration 037 checks effective `has_column_privilege` values and the existing RLS policy and aborts if they do not match. Recheck the catalog in Cloud after applying 037.
- Profile birth date and gender visibility are separate, default to `private`, and can be `public`, `followers`, or `private`. Only currently approved followers qualify for the followers audience. The profile post count includes posts the current viewer can read; it excludes hidden posts and inaccessible content.
- Gender changes automatically choose the matching avatar preset when the gender is Nam/Nữ. Unknown or unset gender uses the generic person icon; the manual neutral-avatar selector is removed. The Settings screen owns the three local theme choices (system, light, dark).
- Media cleanup excludes assets attached to both `published` and restorable `hidden` posts during candidate selection and checks again while locking the referenced post row before retirement. A hidden post therefore retains its asset for Restore; media for permanently removed posts still follows the retention cleanup path.
- `admin_moderate_content` applies the report workflow's protected-account rule to both the acting System Admin and every System Admin target, for hide/remove/restore.
- Notification caller inventory: historical reaction/comment/reply/story/follow emitters call `private.emit_notification`; Task 36 follow/message-request/group-invitation triggers add their own calls. Existing post-share and ordinary-message notifications use separate direct-insert triggers (`notify_post_share` and `notify_conversation_message`), so the helper whitelist change did not disable them. Moderation has no current helper caller. The helper allowlist now includes `share`, `message`, and `moderation` to match the existing kind/preference contract; moderation emission remains unused until a product event is defined.
- `private.c_actor` rejects unverified email accounts from chat operations. The existing `private.lock_profile` also requires a confirmed address for onboarding writes. Review the pre-deploy aggregate counts, then keep those users on the existing Auth confirmation/resend/callback flow. Local tests confirm profile verification status remains readable, unverified onboarding and chat are denied, and onboarding/chat resume after confirmation. They do not verify Cloud email delivery or callback redirects.
- The retired-function sweep matches `%group%` but excludes `%conversation%`. Local catalog checks confirm all public Messenger Group RPCs remain executable while non-conversation community-group functions are revoked.
